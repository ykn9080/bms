BMS 기반 스마트빌딩 데모 시스템BMS-based Smart Building Demo System

프로그래머에서 시설관리 입문자로, 두 분야가 만나는 지점인 BMS를 직접 구현해 본 기록입니다.

A record of a former programmer's hands-on attempt to build a BMS, the point where two fields meet, as a facility management beginner.

1. 들어가며1. Introduction

몇 년 동안 저는 프로그래머로 일했습니다. 데이터를 수집하고, 처리하고, 화면에 보여주는 일이었습니다. 지금은 시설관리 분야로 방향을 바꾸는 중입니다. 건물의 전기, 공조, 조명이 어떻게 움직이는지 배우고 있고, 스마트빌딩 분야에 지원하기 위해 이 데모를 만들었습니다.

For several years I worked as a programmer, collecting data, processing it, and showing it on screens. Now I am moving into facility management. I am learning how electrical, HVAC, and lighting systems in buildings operate, and I built this demo to apply for a smart building position.

처음에는 두 분야가 아주 멀다고 생각했습니다. 하나는 코드와 서버, 다른 하나는 기계실과 설비처럼 보였기 때문입니다. 그런데 공부할수록 두 분야가 같은 문제를 다루고 있다는 것을 알게 되었습니다. 바로 센서로 상태를 측정하고, 데이터를 모아 판단하고, 제어하는 일입니다.

At first I thought the two fields were far apart: one was code and servers, the other machine rooms and equipment. The more I studied, the more I saw that they tackle the same problem: measuring conditions with sensors, gathering data, making judgments, and controlling systems.

BMS(Building Management System)는 그 접점에 있습니다. 시설관리자는 BMS 화면에서 건물의 상태를 보고 설비를 제어합니다. 프로그래머는 같은 구조를 데이터 파이프라인과 대시보드로 구현합니다. 저는 이 두 관점을 모두 가지고 있다는 점이 스마트빌딩 업무에 도움이 될 것이라고 믿습니다.

A BMS (Building Management System) sits at that intersection. Facility managers look at BMS screens to understand building conditions and control equipment, while programmers build the same structure as data pipelines and dashboards. I believe having both perspectives will be valuable in smart building work.

2. 프로젝트 목적2. Project Goals

  • 실제 BMS 장비 없이도 건물 데이터의 흐름을 재현하는 것
  • 센서 데이터를 수집, 저장, 분석, 시각화하는 전체 과정을 직접 구성해 보는 것
  • 시설관리 현장에서 쓰이는 이상 감지와 상태 표시 개념을 코드로 옮겨 보는 것
  • To reproduce the data flow of a building without real BMS hardware
  • To build the entire process of collecting, storing, analyzing, and visualizing sensor data myself
  • To translate the anomaly detection and status display concepts used in facility operations into code

실제 센서 대신 가상 데이터를 생성했습니다. 온도, CO2, 습도, 조도, 재실 인원, 전력 사용량을 시나리오에 따라 만들고, 그 데이터가 실제 건물에서 들어온다고 가정하고 시스템을 돌립니다.

Instead of real sensors, I generated virtual data. Temperature, CO2, humidity, illuminance, occupancy, and power consumption are produced according to scenarios, and the system runs as if that data came from a real building.

3. 시스템 구성3. System Architecture

전체 구성은 Docker Compose로 한 번에 실행되는 5개의 서비스로 이루어져 있습니다. 외부에 공개되는 것은 Nginx뿐이고, 나머지 서비스는 서버 내부에서만 동작합니다.

The whole system consists of five services that start together with Docker Compose. Only Nginx is exposed externally; the other services run solely inside the server.

보안 측면에서는 Nginx 외에는 모든 포트를 127.0.0.1에만 열어 두었습니다. 시설 시스템은 외부에 직접 노출되면 안 된다는 원칙을 반영한 것입니다.

From a security standpoint, every port except Nginx is bound only to 127.0.0.1. This reflects the principle that facility systems should never be directly exposed to the outside.

4. 모니터링 화면4. Monitoring Dashboard

Grafana로 만든 최종 모니터링 화면입니다. 상단에는 온도, CO2, 습도, 조도를 게이지로 보여줍니다. 가운데에는 시나리오 버튼(Hot, Cold, Humid, CO2, Lighting)으로 상황을 만들고, 설비 상태(Chiller, Heater, Humidifier, Dehumidifier, AHU)를 확인할 수 있습니다. 하단에는 층별 재실 인원, 조명 요약, 전력 사용량, 습도, CO2, 조도 추이 그래프가 있습니다.

This is the final monitoring screen built with Grafana. The top shows temperature, CO2, humidity, and illuminance as gauges. The middle lets you create situations with scenario buttons (Hot, Cold, Humid, CO2, Lighting) and check equipment status (Chiller, Heater, Humidifier, Dehumidifier, AHU). The bottom shows occupancy by floor, a lighting summary, and trend graphs for power consumption, humidity, CO2, and illuminance.

시설관리 입문자 입장에서 가장 신경 쓴 부분은 상태 표시입니다. 정상, 이상, 장비 작동을 나누어 보여주고, 이상 상황이 생기면 상태 문구가 바뀌도록 했습니다. 현장에서 관리자가 가장 먼저 보는 것이 이런 정보라고 생각했습니다.

As a facility management beginner, I focused most on status display. The screen separates normal, abnormal, and equipment-running states, and the status message changes when an abnormal condition occurs. I think this is the information managers look at first in the field.

5. Node-RED 흐름과 AWS IoT MQTT5. Node-RED Flow and AWS IoT MQTT

백엔드의 중심은 Node-RED입니다. 데이터 생성, 판단, 저장, 전송을 모두 하나의 흐름(flow)으로 구성했습니다.

At the center of the backend is Node-RED. Data generation, judgment, storage, and transmission are all composed as a single flow.

흐름은 크게 세 부분으로 나뉩니다.

The flow is broadly divided into three parts.

5-1. 데이터 생성과 판단 (상단 흐름)5-1. Data Generation and Judgment (upper flow)

5초마다 트리거가 발생하면 다음 순서로 데이터가 만들어집니다.

Every five seconds a trigger fires, and data is produced in the following order.

  1. 명령입력: 사용자가 보낸 시나리오 명령을 받습니다.
  2. 시나리오엔진: Hot, Cold, CO2 등 선택된 상황에 맞는 값을 계산합니다.
  3. 재실인원생성: 층별 재실 인원을 만듭니다.
  4. Lux 계산: 재실 인원과 조명 상태를 바탕으로 조도를 계산합니다.
  5. 출력생성: 온도, 습도, CO2, 조도, 전력 값을 하나의 메시지로 묶습니다.
  6. 이상 데이터 판별: 기준 범위를 벗어난 값만 골라냅니다.
  1. Command input: Receives the scenario command sent by the user.
  2. Scenario engine: Calculates values matching the selected situation, such as Hot, Cold, or CO2.
  3. Occupancy generation: Creates occupancy counts by floor.
  4. Lux calculation: Computes illuminance from occupancy and lighting state.
  5. Output generation: Bundles temperature, humidity, CO2, illuminance, and power values into one message.
  6. Anomaly detection: Selects only values outside the defined thresholds.

판별 결과에 따라 흐름이 갈라집니다. 모든 데이터는 AWS IoT Publish로 클라우드에 전송되고, 이상 데이터만 PostgreSQL에 저장됩니다. 정상 데이터까지 모두 관계형 DB에 넣으면 저장 공간과 조회 비용이 커지기 때문입니다. 이 부분이 제가 설계하면서 가장 많이 고민한 지점입니다.

The flow then branches based on the judgment. All data is sent to the cloud via AWS IoT Publish, while only abnormal data is stored in PostgreSQL. Storing every normal reading in a relational database would increase storage and query costs. This was the point I thought about most during the design.

5-2. AWS IoT MQTT 발행과 구독 (하단 흐름)5-2. AWS IoT MQTT Publish and Subscribe (lower flow)

이 프로젝트의 핵심은 MQTT를 통한 발행과 구독입니다. 실제 BMS 장비와 상위 시스템이 데이터를 주고받는 방식과 같은 구조를 AWS IoT Core로 구현했습니다.

The core of this project is publishing and subscribing over MQTT. I implemented, with AWS IoT Core, the same structure that real BMS devices and upper-level systems use to exchange data.

  • Publish: Node-RED가 생성한 센서 데이터를 AWS IoT Core의 토픽으로 발행합니다. 전등 상태도 별도 토픽으로 발행합니다.
  • Subscribe: 같은 토픽을 구독하여 클라우드를 거쳐 되돌아온 데이터를 받습니다.
  • 저장: 구독한 데이터는 influxdb_save 노드를 통해 InfluxDB에 시계열로 저장됩니다.
  • 조회: influxdb_read 노드가 InfluxDB에서 최근 데이터를 읽어 대시보드용 형식으로 가공합니다.
  • Publish: Publishes the sensor data generated by Node-RED to topics in AWS IoT Core. Lighting status is published on a separate topic.
  • Subscribe: Subscribes to the same topics and receives the data that returns through the cloud.
  • Storage: The subscribed data is stored as time series in InfluxDB through the influxdb_save node.
  • Query: The influxdb_read node reads recent data from InfluxDB and reshapes it for the dashboard.

이렇게 하면 데이터는 발행 → 클라우드 → 구독 → 저장 → 조회 → 시각화의 경로를 거칩니다. 이 과정은 실제 IoT 시스템에서 장비 데이터가 처리되는 흐름과 같습니다. 시설관리자 입장에서는 "센서 값이 어디서 와서 어디에 쌓이고 화면에 어떻게 보이는가"를 한눈에 볼 수 있는 구조입니다.

In this way, data follows the path publish → cloud → subscribe → store → query → visualize. This mirrors how device data is processed in real IoT systems. From a facility manager's perspective, the structure makes it easy to see where a sensor value comes from, where it is stored, and how it appears on screen.

5-3. 대시보드 연결과 상태 응답 (우측 및 좌상단 흐름)5-3. Dashboard Connection and Status Response (right and upper-left flows)

  • dashboard용 data: InfluxDB에서 읽은 데이터를 게이지와 차트에 맞게 나눕니다.
  • switch: 온도, 습도, 조도, CO2 값을 각각의 게이지로 보냅니다.
  • Token_Chk, 403, OK: 상태 확인 요청에 대해 토큰을 검사하고, 통과하지 않으면 403으로 응답합니다. 외부에서 임의로 명령을 보내지 못하도록 한 장치입니다.
  • status return, Response: 현재 상태를 요청한 쪽에 돌려줍니다.
  • dashboard data: Splits the data read from InfluxDB to fit the gauges and charts.
  • switch: Routes temperature, humidity, illuminance, and CO2 values to their respective gauges.
  • Token_Chk, 403, OK: Checks a token on status requests and responds with 403 if it does not pass. This prevents arbitrary commands from outside.
  • status return, Response: Returns the current status to the requester.

7. 프로그래머에서 시설관리로7. From Programmer to Facility Management

이 프로젝트를 만들면서 두 분야의 공통점과 차이를 함께 배웠습니다.

Building this project taught me both the common ground and the differences between the two fields.

  • 공통점: 센서 데이터를 기준값과 비교해 이상을 판단하는 구조는 소프트웨어의 조건 분기와 같습니다. 데이터를 모으고 시각화하는 방식도 같습니다.
  • 차이점: 시설에서는 값이 맞는지보다 그 값이 설비와 사람에게 어떤 의미인지가 더 중요합니다. 예를 들어 CO2 수치가 높다는 것은 환기 설비의 문제일 수도 있고 재실 인원이 많다는 뜻일 수도 있습니다.
  • Common ground: Judging anomalies by comparing sensor data against reference values is structurally like conditional branching in software. Collecting and visualizing data is also similar.
  • Differences: In facilities, what matters more than whether a value is correct is what that value means for equipment and people. For example, a high CO2 reading could indicate a ventilation problem or simply a large number of occupants.

프로그래밍 경험은 데이터 흐름을 설계하고 자동화하는 데 도움이 되었습니다. 시설 지식은 그 데이터가 건물에서 어떤 의미를 가지는지 해석하는 데 필요합니다. 스마트빌딩은 이 두 능력이 함께 필요한 분야라고 생각합니다.

My programming experience helped me design and automate data flows. Facility knowledge is needed to interpret what that data means within the building. I believe smart buildings are a field that requires both of these abilities together.

8. 향후 계획8. Future Plans

  • 실제 BMS 장비(예: Modbus 기반 센서)와 연동하여 가상 데이터를 실데이터로 교체
  • 기준값과 이상 판단 로직을 시설 기준에 맞춰 보완
  • 에너지 사용량 분석과 설비별 운전 이력 기능 추가
  • 이상 발생 시 알림 기능 구현
  • Replace virtual data with real data by integrating actual BMS devices (for example, Modbus-based sensors)
  • Refine reference values and anomaly logic to match facility standards
  • Add energy usage analysis and per-equipment operation history
  • Implement alert notifications when anomalies occur

9. 마치며9. Closing

이 데모는 완성된 시스템이라기보다, 시설관리와 IT가 만나는 지점을 직접 확인해 본 실험입니다. 프로그래머로서 익힌 데이터 처리 능력과, 시설관리 현장에서 배우고 있는 설비에 대한 이해를 하나의 BMS 안에 담아 보았습니다. 앞으로 스마트빌딩 현장에서 이 두 가지를 함께 활용하고 싶습니다.

This demo is less a finished system than an experiment to see for myself where facility management and IT meet. I tried to bring together the data processing skills I developed as a programmer and the understanding of building systems I am learning in facility management, within a single BMS. I hope to put both to use in smart building work ahead.
